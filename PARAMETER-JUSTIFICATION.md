## 1. Stagnation Detection

### What It Does

Stagnation detection is a watchdog mechanism that fires when the best-seen fitness does not improve for 10 consecutive evaluations. Upon triggering, it overrides the Thompson Sampling arm selection and forces the algorithm to try a different class of operator. The counter resets as soon as any improvement is found or the override fires.

**Implementation (core.py):**

```python
# Initialization — core.py:216-219
self._stagnation_counter = 0
self._stagnation_threshold = 10
self._best_fitness_at_last_improvement = -float('inf')

# Detection & override — core.py:343-368
if self._stagnation_counter >= self._stagnation_threshold:
    refine_arms  = [a for a in self.bandit.arm_names if a in ("refine", "simplify")]
    explore_arms = [a for a in self.bandit.arm_names if a in ("crossover", "random_new")]

    refine_mean  = max((bandit_arms[a].posterior_mean for a in refine_arms),  default=0.0)
    explore_mean = max((bandit_arms[a].posterior_mean for a in explore_arms), default=0.0)

    if refine_mean >= explore_mean and refine_arms:
        override_pool = refine_arms    # exploit: bandit thinks refinement is better
    elif explore_arms:
        override_pool = explore_arms   # explore: bandit thinks exploration is better
    else:
        override_pool = self.bandit.arm_names

    operator_name = random.choice(override_pool)
    self._stagnation_counter = 0      # reset immediately
else:
    operator_name, theta = self.bandit.select_arm()

# Tracking — core.py:427-432
if child.fitness > self._best_fitness_at_last_improvement:
    self._best_fitness_at_last_improvement = child.fitness
    self._stagnation_counter = 0
else:
    self._stagnation_counter += 1
```

### Why It Was Added

**1. Not in the DTS Paper — GA-LLAMEA-specific engineering addition.**
The original Discounted Thompson Sampling paper (Qi et al., 2023) was designed and validated for T = 100,000+ evaluations. In that setting, stagnation is self-correcting through the discount factor alone because the bandit has thousands of pulls to recover. GA-LLAMEA runs at T = 100 — a regime the paper never analyzed. With only 100 evaluations, a 10-step dead zone (10% of budget) is already catastrophic and unlikely to self-resolve.

**2. LLM outputs are high-variance and bursty.**
Unlike classical fitness functions, code generated by an LLM can produce a long plateau of near-identical outputs followed by a sudden structural breakthrough. This makes the distribution of fitness improvements non-Gaussian and heavily right-tailed. The 10-step threshold ensures the mechanism is not too sensitive (does not fire on ordinary noise) but also does not wait indefinitely.

**3. Threshold of 10 matches n_offspring.**
The main experimental configuration uses `n_offspring=8` (offspring per generation). A stagnation window of 10 therefore spans slightly more than one complete generation, giving the bandit a natural "one generation with no progress" trigger before intervening.

**4. Override is bandit-informed, not random.**
The override does not blindly force random exploration. It reads the current posterior means from both arm pools (refine/simplify vs. crossover/random_new) and directs the override toward whichever pool the bandit currently rates higher. This preserves the bandit's learned information while still forcing a non-habitual choice.

**5. Self-resetting prevents over-correction.**
The counter resets on override (not just on improvement), so the mechanism cannot lock the algorithm into a permanent forced-exploration mode. One override is the full intervention.

## 2. Epsilon Exploration = 0.15

### What It Does

`epsilon_exploration` is an epsilon-greedy floor added on top of Discounted Thompson Sampling. With probability `epsilon_exploration`, an arm is selected uniformly at random instead of using Thompson Sampling. At 0.15, this means 15% of post-burn-in selections are random and 85% follow learned posterior probabilities.

```python
# bandit.py:185-194
if self.epsilon_exploration > 0 and random.random() < self.epsilon_exploration:
    chosen_arm = random.choice(self.arm_names)
    # posteriors still updated for all arms — just selection is random
    return chosen_arm, self.arms[chosen_arm].last_theta
```

This feature is **not in the DTS paper** — it is a GA-LLAMEA practical extension specifically to prevent arm extinction in very small budgets.

### Why Not Pure Thompson Sampling (epsilon = 0)?

With K = 4 arms and budget T = 100, pure Thompson Sampling (epsilon = 0) can permanently starve low-performing arms by evaluation 20-30. In the LLM setting this is dangerous because operator quality is **non-stationary**: an arm that was poor in generation 1 (e.g., crossover when the population has no diversity) may become the best arm in generation 5 (after diversity is established). Once an arm has zero pulls, its posterior cannot update and Thompson Sampling will never select it again — pure arm extinction.

From `GA-LLAMEA-IMPLEMENTATION.md` §3.6:
> "Epsilon-greedy floor: Prevents permanent arm extinction. Without this, a single bad early batch can eliminate an arm from consideration permanently within the 100-evaluation budget."

### Why 0.15, Not 0.4?

The default in `bandit.py` is `epsilon_exploration=0.4`. Earlier experiments (refine-vs-norefine, 3ARM-vs-4ARM ablations) used this default. The problem was diagnosed in the improvement plan:

> **With epsilon = 0.4:** Only 60% of selections use Thompson Sampling. With discount = 0.99 and gamma decay, this leaves the bandit making decisions on an effective sample size of only 2–4 observations per arm. Thompson Sampling under these conditions is functionally random.
> *(GA-LLAMEA-IMPROVEMENTS-SUMMARY.md, lines 151-161)*

The shift to **0.15** was a deliberate move to let the bandit dominate selection (85% Thompson Sampling) while preserving a minimum exploration floor sufficient to keep all four arms alive. The DTS tuning script (`run-dts-tuning.py`) uses epsilon = 0.1 as its default, and ABLATION-PROMPTS-CROSSOVER experiments used 0.1. The settled value of **0.15** represents the final experimental configuration after this progression.

## 3. Discount Factor = 0.99

### Clarification: This Is Not 0.15

The `discount` parameter (gamma, γ) is set to **0.99** in all experiments. The value 0.15 does not appear as a discount factor anywhere in the codebase or experiment logs. All `experimentlog.jsonl` files confirm `"discount": 0.99`.

### What It Does

The discount factor implements exponential forgetting in the Discounted Thompson Sampling algorithm. After each round, accumulated arm statistics are multiplied by gamma:

```python
# bandit.py:266-278
def _apply_discount(self) -> None:
    for arm_state in self.arms.values():
        arm_state.discounted_count *= self.discount   # N  *= γ
        arm_state.discounted_sum   *= self.discount   # μ~ *= γ
        arm_state.discounted_sum_sq *= self.discount
```

This causes old observations to contribute exponentially less over time, allowing the bandit to track non-stationary reward distributions.

### Why 0.99

**Effective memory window = 1/(1 − γ)**

With γ = 0.99:
```
Effective Memory ≈ 1 / (1 - 0.99) = 100 steps
```

This is mathematically matched to the experiment budget (T = 100). The bandit's effective memory spans exactly the entire run, meaning no observation is fully discarded within the budget, but more recent observations are weighted higher. This is the ideal balance for a 100-evaluation experiment:

- **Too aggressive (γ = 0.9):** Effective memory = 10 steps. With 4 arms and only 10 effective observations, each arm has ~2.5 effective data points — statistically meaningless.
- **No discount (γ = 1.0):** No adaptation. Late-run phase changes (early exploration → late refinement) are not reflected in arm selection.
- **γ = 0.99:** Entire history is relevant, but the most recent breakthroughs are weighted higher. Acts like a Bayesian optimizer responsive to current population quality.

From `GA-LLAMEA-DTS-Defense.md`:
> "This tuning is mathematically perfect for our budget. It means the bandit considers the entire history of the run as relevant... but it still weights recent successes slightly higher. This allows it to act like a standard Bayesian optimizer that is responsive to the latest generation's breakthroughs without discarding early lessons."

**Why not use the paper's formula?**
Qi et al. (2023) recommend γ = 1 − √(B_T/T) where B_T is the number of breakpoints (non-stationary phase changes). B_T is unknown in LLM evolution — there is no oracle for how many times operator quality will shift within a run. The fixed value γ = 0.99 is a practical conservative choice that works well empirically for T = 100 across all tested problem instances.

### Non-Stationarity Justification

The non-stationarity argument is the core reason DTS (rather than a stationary bandit) was chosen at all. Operator quality in evolutionary algorithms is deeply phase-dependent:

| Phase | Best operator | Reason |
|-------|---------------|--------|
| Early (evals 1-20) | `random_new`, `crossover` | Population has no quality yet; need diversity |
| Mid (evals 20-60) | `refine` | Good solutions exist; incremental improvement is most efficient |
| Late (evals 60-100) | `simplify` | Solutions are complex; simplification improves generalization |

This pattern is directly visible in the bandit final states above: `simplify` and `refine` dominate late-run pull counts (32-43 pulls each) while `random_new` and `crossover` trail (6-16 pulls), consistent with the prediction that exploration operators are most useful early and the bandit correctly down-weights them as the run progresses.

## 4. Combined Effect: Why These Three Parameters Work Together

The three mechanisms form a layered defense against the pathologies of small-budget LLM optimization:

```
Layer 1: discount=0.99
   → Effective memory = 100 = full budget
   → Bandit can track phase changes without forgetting useful history

Layer 2: epsilon_exploration=0.15
   → 15% forced random selection
   → Prevents arm extinction when bandit becomes overconfident
   → Keeps all arms statistically alive even if posterior pushes toward one arm

Layer 3: stagnation_threshold=10
   → Hard override after 10 flat evaluations
   → Fires when bandit's preferred arm is genuinely stuck
   → Redirects toward the other arm class (exploit ↔ explore) based on posterior
```

Without stagnation: the algorithm can get permanently trapped on a plateau within the 100-eval budget.
Without epsilon=0.15: an arm that is unlucky early dies permanently, blocking future recovery.
Without discount=0.99: the bandit over-forgets, treating each generation as independent and losing the ability to exploit learned preferences.
